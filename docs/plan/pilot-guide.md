# 시범 운영 안내서(4단계)

시범 운영 동안 선생님(시트 소유자)과 학사 교사가 지킬 것·확인할 것을 한곳에 모았습니다. 항목마다 **왜**를 한 줄 붙였습니다.
이미 다른 문서에 있는 절차는 옮겨 적지 않고 링크만 둡니다.

- 처음 설치·로그인 확인: [`docs/stage0-checklist.md`](../stage0-checklist.md)
- 기능별 확인 순서: [`docs/design/stage2-teacher-checks.md`](../design/stage2-teacher-checks.md) · [`docs/design/stage3-teacher-checks.md`](../design/stage3-teacher-checks.md)
- 알려진 한계 목록: [`docs/plan/followups.md`](followups.md)

---

## 1. 시작 전 한 번(소유자)

| 할 것 | 왜 |
|---|---|
| 웹앱을 **'나(소유자)로 실행'** 으로 배포한다. 배포 화면의 "다음 사용자 인증 정보로 실행"이 '나'인지 확인 | 데이터 시트는 아무와도 공유하지 않으므로, 웹앱이 소유자 권한으로 읽고 써야 한다. '접속한 사용자로 실행'이면 백업 같은 소유자 전용 함수의 확인이 누구에게나 통과한다(점검 #7) |
| 스크립트 속성 **`DIAG_ENABLED`를 `false`로**(또는 지움) | 0단계에서 쓴 진단 화면(`diagPing`)을 닫는다. 켜 두면 필요 없는 정보 창구가 하나 남는다 |
| **매일 백업 켜기:** 편집기에서 `installNightlyBackup` → `runBackupNow`를 실행하고 결과 확인 — 절차는 stage2 확인표 **A5** | 시범 운영 중 실수로 기록이 꼬여도 하루 전 사본으로 되돌릴 수 있다. 사본은 공유되지 않은 채 30일 보관된다(결정 65) |
| 데이터 시트·백업 폴더의 **공유 버튼이 '나만'** 인지 확인 | 학생·학부모 정보가 들어 있다(CLAUDE.md 2). 웹앱만 데이터에 접근한다 |
| 학사 교사·출결 담당·근무표 담당·담임 계정이 `users` 탭에 있고 역할이 맞는지 화면(관리자 홈)으로 확인 | 권한은 서버가 이 역할로 판정한다. 역할이 틀리면 버튼이 보여도 저장이 막히거나, 반대로 볼 필요 없는 것을 본다 |

## 2. 매일(근무교사·출결 담당)

| 할 것 | 왜 |
|---|---|
| 출결 담당은 그날 사전 특이사항을 확정한 뒤 출석부를 인쇄한다 | 미인정 지각·조퇴·결석을 확정하면 자동 1OUT이 생긴다. 확정 전 출석부에는 반영되지 않는다 |
| 근무 교대는 **근무 시작 전에** 한다. 이미 시작한 근무가 바뀌었으면 본인이 넘기지 말고 **근무표 담당자에게 '대신 근무'로 기록**해 달라고 한다(결정 66) | 시작 뒤에 넘기면 이미 근무한 기록과 그날 OUT 입력 권한이 근무하지 않은 사람에게 옮겨 간다 |
| 저장할 때 **"확인한 뒤 다른 변경이 있었습니다" / "목록을 새로 불러와 주세요" / "다른 사람이 저장 중입니다"** 가 뜨면: 화면을 새로 불러온 뒤 내용을 다시 확인하고 저장한다. 같은 버튼을 여러 번 누르지 않는다 | 다른 선생님이 같은 학생·같은 자리를 방금 바꿨다는 뜻이다. 새로 불러오지 않고 다시 누르면 그 변경을 모르고 덮어쓸 수 있어서 서버가 일부러 막은 것이다 |
| **재입실한 학생**이 있으면, 재입실 뒤 며칠 동안 그 학생의 **급식 값(조식·석식)을 학생 기록 화면에서 한 번 확인**한다 | 재입실 기록 뒤에 그 학생의 급식 신청이 여러 건 얽히면 입력 순서에 따라 재입실 뒤 급식 값이 다르게 남는 드문 경우가 있다(알려진 한계 Y2·Q). 틀렸으면 급식 변경 신청 한 건으로 바로잡힌다 |
| 데이터 시트 탭은 **손으로 고치지 않는다.** 고칠 것이 있으면 웹앱 화면에서 고친다 | 여러 줄을 한 번에 저장할 때 탭 전체를 다시 쓰므로, 손으로 넣은 날짜·수식 칸이 글자로 바뀔 수 있고 감사 기록에도 남지 않는다(점검 #8) |

## 3. 매주(소유자)

| 할 것 | 왜 |
|---|---|
| 백업 폴더에 지난 7일 사본이 날마다 하나씩 있고, 공유 표시가 없는지 본다. `audit_log`에서 `backup:ok` 줄을 확인 | 트리거가 멈추거나 권한이 풀리면 백업이 조용히 멈출 수 있다 |
| `audit_log`에서 `denied:` 줄을 훑어본다 | 등록 안 된 계정이 들어오려 했거나, 등록된 선생님이 권한 밖 기능을 눌렀다는 기록이다. 역할을 잘못 준 것인지 바로 알 수 있다 |
| 식수 집계 화면과 실제 급식 인원을 하루 골라 맞춰 본다 | 급식 규칙(적용일·퇴실 뒤 석식 중단)이 실제 운영과 맞는지 시범 운영에서 확인해야 할 가장 중요한 숫자다 |
| 이상하다고 느낀 일을 날짜·학생(이름 대신 학번 끝자리)·화면과 함께 적어 둔다 | 재현할 수 있어야 고칠 수 있다. 실제 학생 정보는 대화·문서에 그대로 옮기지 않는다(CLAUDE.md 1) |

## 4. 이상할 때 — 무엇을 보고 누구에게 알릴지

| 보이는 것 | 먼저 볼 곳 | 할 일 / 알릴 곳 |
|---|---|---|
| "같은 id의 줄이 여러 개라 고칠 수 없습니다" | 메시지에 나온 탭 | 탭을 손으로 복사·붙여넣기 했을 때 생긴다. 소유자가 편집기에서 `repairDuplicateIds()`(미리보기, 아무것도 안 바꿈)로 확인한 뒤 `repairDuplicateIds(true)`로 고친다 — 기존 행은 그대로 두고 중복 줄에만 새 id를 준다 |
| 학생의 급식·학사 상태가 기대와 다름 | 학생 기록 화면(급식·입퇴실 기록) | 재입실 학생이면 2절 Y2 항목. 아니면 신청 일시·적용일을 기록과 함께 개발 담당(총괄)에게 알린다 |
| 자동 OUT이 생기거나 사라진 이유를 모르겠음 | OUT 목록의 사유, 사전 특이사항의 확정·취소 기록 | 특이사항을 확정·취소하면 OUT이 따라간다. 설정의 자동 OUT 유형을 바꾸면 **바꾼 뒤** 확정한 것부터만 적용된다(결정 40) |
| 근무자·교대가 틀림 | 근무표 화면 | 근무표 담당자에게. 이미 지난 근무는 담당자·관리자만 고칠 수 있다(결정 66) |
| 백업 사본이 없거나 공유 표시가 있음 | 백업 폴더, `audit_log`의 `backup:` 줄 | 소유자가 `runBackupNow`를 다시 실행. 공유 표시가 있으면 바로 '나만'으로 바꾸고 총괄에게 알린다 |
| 화면이 멈추거나 "6분" 시간 초과 | 어느 화면·몇 명 분량이었는지 | 총괄에게 알린다(명단 업로드·식수 집계처럼 많은 줄을 한 번에 다루는 화면이 후보) |
| 권한이 없다고 나오는데 있어야 함 | 관리자 홈의 계정 목록(역할·담당 학생·담임 반) | 소유자가 `users` 역할이나 `enrollments` 담당교사를 확인. 화면에서 버튼을 숨기는 것은 보안이 아니라 편의이고, 판정은 늘 서버가 한다 |

알려진 한계(고치지 않고 사람이 확인하는 것): 재입실 전후 급식 신청이 얽힌 경우(Q·Y2 — 2절에서 확인), 퇴실 취소로 되돌아오지 않는 막힌 신청서(다시 입력). 자세한 것은 [`followups.md`](followups.md) '급식·입퇴실 저장' 절.
