# F11 출결 결과 정리 격자 — 코딩A 준비 메모 (C33, R22·D12 전)

> 2026-11-17 코딩A. 지금 특이사항 저장 경로(`Exceptions.gs`, `AutoOuts.gs`)를 결과 입력에 **그대로** 쓰려면 무엇이 필요한지 정리한 짧은 메모입니다. 코드는 R22(격자 모델)·D12(시안)가 병합된 뒤 시작합니다. 결론: **저장 방식은 그대로 쓰되 "여러 칸을 한 번에" 쓰는 함수 한 쌍이 새로 필요하고, 읽기는 서버가 칸 코드까지 계산해 내려 줘야 합니다.**

## 1. 지금 경로로 되는 것

- **새 탭이 필요 없다.** 결과(×·△·조)는 `exceptions_<기간>` 행으로 쓴다: 유형 `미인정결석`·`미인정지각`·`미인정조퇴`(자동 1OUT 유형) 또는 인정 유형(`병결`·`병지각`·`병조퇴` 등). 행에는 `blocks`(칸의 시간대 또는 `ALL`), `reason`, `status`가 이미 있다. (PRD의 `attendance_results` 탭은 만들지 않는다 — stage5.md.)
- **확정 상태로 한 번에 저장**은 이미 된다: `exception.confirm` 권한(관리자·출결 담당)이면 `saveException`이 `status '확정'`·`confirmed_by/at`을 같이 쓴다. 결과 입력은 이 권한만 허용하면 된다(담당교사·담임은 보기만 — PRD 권한표). 새 권한 키는 필요 없다(보기 = `exception.view`(넓은 보기), 쓰기 = `exception.confirm`).
- **자동 1OUT 연결**은 저장 뒤 `vioAfterExceptionWrite_`가 맞춘다(미인정 유형 확정 → OUT 생성, 취소 → OUT 취소, 같은 유형 재저장은 건드리지 않음). 이 함수는 학생 여러 명·묶음 여러 개를 받는다(`studentIds`, `touchedGroups`).
- **고치기 = 취소 + 새 행**은 `cancelException(…, onlyDate)`가 이미 한다(행은 지우지 않고 `status 취소` + `cancel_reason`, audit에 남음).

## 2. 그대로는 안 되는 것 (새로 필요한 것)

| 문제 | 왜 | 필요한 것 |
| --- | --- | --- |
| **한 번에 한 학생·한 유형 묶음만 쓴다** | `saveException`은 학생 1명·날짜 범위 1개·유형 1개다. 주말 정리는 학생 수십 명 × 칸 수십 개다. 칸마다 부르면 락을 칸마다 잡고, 칸마다 자동 OUT 맞추기(기간 특이사항·OUT·근무표를 다시 읽음)가 돈다 → 느리고 6분 한도·락 대기(10초)에 걸린다 | **`previewAttendanceResults(payload)` / `saveAttendanceResults(payload, sig)`**: **락 하나**, 새 행은 `bulkAppend_` 한 번, 취소할 행은 `bulkUpdateRecords_` 한 번, **자동 OUT 맞추기 한 번**(`studentIds` 전체, `touchedGroups` = 새 묶음 전부), 메일은 락 밖에서 한 번 |
| **"같은 칸 다시 고치기"가 사유 입력을 요구한다** | `cancelException`은 취소 사유 2자 이상 필수. 격자에서 칸을 고칠 때마다 사유를 묻기 어렵다 | 결과 정리가 쓰는 취소 사유는 자동 문구(예: "결과 정리에서 고침")로 기록. 사용자가 적은 사유는 새 행의 `reason`(메모)에 |
| **고칠 때 OUT 면담 연결이 끊길 수 있다** | 같은 칸을 취소 + 새 행으로 바꾸면 자동 OUT이 취소되고 새 id로 다시 생긴다. 이미 면담에 연결된 OUT(결정 51)이면 연결이 끊긴다 | **바뀐 칸만** 취소 + 새 행(저장 때 칸별로 이전 코드와 비교해 같으면 건드리지 않는다). 2OUT·면담이 걸린 학생의 칸을 고치면 미리보기에서 경고 |
| **묶음(group)이 1OUT 단위다**(결정 22) | 같은 `group_id`는 1OUT. 격자에서 칸마다 묶음을 따로 만들면 하루 두 블록 결석이 2OUT, 한 묶음으로 만들면 연속 결석 며칠이 1OUT이 될 수 있다 | **R22/총괄 결정 필요(아래 질문 1)** — 제안: 같은 학생·같은 날의 칸은 한 묶음(하루 1OUT), 날짜가 다르면 다른 묶음 |
| **읽기 크기** | 월 격자 = 180명 × 31일 = 5,580칸. 칸 객체를 그대로 내려 주면 응답이 크고 화면이 느리다 | 서버가 **칸 코드 문자열**(○·×·△·조·학·가·병… 한두 글자)을 **학생 줄 × 날짜 열 문자열 배열**로 내려 주고(학생 id 순서·날짜 목록 따로), 칸 상세(유형·사유·입력자)는 칸을 누를 때 한 칸씩 |
| **낡은 화면** | 두 출결 담당이 같은 주를 동시에 정리할 수 있다 | 읽을 때 범위(주·월)의 행 표(`id|updated_at` 해시, 서류·근무·일정에서 쓴 방식) + 칸별 이전 코드(`expect`)를 받고, 락 안에서 같은 범위로 다시 계산해 다르면 `{stale:true, 바뀐 칸}`·쓰기 0 |

## 3. 읽기 성능 (재야 할 것)

- 한 번 읽는 것: 이번 기간 `exceptions_<기간>`(학기 전체, 수천 행까지), `fixed_schedules`(그 달 확정), `enrollments`·`students`(180명), 상태(`status_changes`, 입실 전·퇴실 후 날짜 칸 처리). `readAll_`는 실행당 한 번 읽고 캐시하므로 **탭 읽기는 몇 번**이다. 칸 계산은 R22의 순수 함수(출석부와 같은 판정)가 한다.
- **리허설(T4a, 학생 100명 이상)에서 `getAttendanceGrid` 한 달 응답 시간·크기를 먼저 잰다.** PRD 성공 기준(홈 3초)과 별개로 격자는 "주 단위 기본, 월은 보기만"으로 시작하는 안도 있다. 기준: 주 1.5초, 월 3초 안(가정 — 재 본 뒤 정함).
- 한 번 저장 한도: 칸 입력은 대부분 예외(결석·지각·조퇴)뿐이라 **○ 출석은 행을 쓰지 않는다**. 저장 payload는 "바뀐 칸 목록"으로 한정하고 상한(예: 500칸)을 둔다 — `EXC_MAX_DAYS`(62일)는 격자 저장에는 맞지 않아 칸 수 상한으로 대체.

## 4. 새 공개 함수 후보

| 함수 | 권한 | 하는 일 |
| --- | --- | --- |
| `getAttendanceGrid(range)` | `exception.view`(넓은 보기: 출결 담당·관리자 전체, 학사 교사 담당 학생, 담임 자기 반) | 주·월 격자(칸 코드 배열 + 학생·날짜 순서 + 범위 토큰 + 학생별 누적) |
| `getAttendanceCell(studentId, date)` | 같은 키, 학생 범위는 서버가 판정 | 칸 상세(칸마다 사전 특이사항·결과의 유형·사유·입력자) |
| `previewAttendanceResults(payload)` | `exception.confirm` | 바뀌는 칸 수, 새로 생기는/취소되는 OUT 수, 2OUT·면담 경고, 겹침 경고 — 쓰지 않음, sig |
| `saveAttendanceResults(payload, sig)` | `exception.confirm` | 위 한 번 저장(락 하나). 학년도·기간이 끝났으면 거부(`EXC_ENDED_MSG`, 질문 3) |

`get…` 이름은 `phone_leak` 감시 시험이 모든 역할로 자동으로 훑는다(전화번호가 응답에 없는지). 새 공개 함수는 `tests/public-api.d/coding-a.json`에 등록한다.

## 5. 시험 계획 (코드 때)

- R4(gas-fakes): 권한(출결 담당·관리자만 저장, 나머지 거부 + `denied:exception.confirm`), 락 하나(`strictLock`), stale(두 사람 같은 칸·같은 주), 바꾸지 않은 칸은 쓰기 0, 미인정 결과 저장 → 1OUT 생성·취소 → 1OUT 취소·같은 유형 재저장 → OUT 유지(면담 연결 유지), 2OUT 경고, 칸 수 상한, 이번 기간 비등록 학생·입실 전·퇴실 후 칸 거부, audit(`bulk_create`·`bulk_update` + 요약 한 줄 `attendance:grid`).
- 읽기: 격자 칸 코드 = 출석부 칸 판정과 같은 표(R22 오라클과 대조), 응답에 이름·이메일·전화 없음(학생은 id·표시 이름만).
- 리허설: 학생 100명 이상 한 달 읽기·쓰기 시간.

## 6. 먼저 정해야 할 질문 (총괄·R22)

1. **묶음 단위**: 격자로 입력한 결과는 "같은 학생·같은 날 = 한 묶음(1OUT)"으로 둘까요? (제안: 예. 며칠 연속 결석도 날마다 1OUT.) 결정 22와 맞는지.
2. **자동 OUT 메일**: 지금은 OUT이 생길 때마다 담당교사·담임 등에게 메일이 간다(결정 49). 주말에 한꺼번에 정리하면 **메일이 수십 통**이 되고 이미 지난 일이다. 격자 저장은 학생 단위로 모아 한 통으로 보낼까요, 보내지 않을까요?
3. **끝난 기간**: 학기 마지막 주 정리는 학기가 끝난 뒤일 수 있다. 끝난 기간은 읽기만(지금 규칙) 두면 마지막 주를 정리할 수 없다. 종료 후 N일(예: 14일)까지 쓰게 할까요?
4. **인정 결과 유형**: ×·△·조 옆에서 인정(병결 등)인지 미인정인지 고르는 목록은 `exception.types` 설정을 따른다. 설정에서 이름을 바꾸면 격자의 기호 대응이 어긋나므로 **R22가 대응표를 상수로 둘지(이름 검사) 설정으로 둘지** 정해 주세요.
5. **사전 특이사항이 있는 칸에 결과 입력**: 겹침 경고 후 두 건으로 두는지(지금 `saveException`처럼), 사전 특이사항을 결과가 대체하는지.
